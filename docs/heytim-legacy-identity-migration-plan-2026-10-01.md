## Priority 3: physical resources requiring a separate migration

- **Amplify:** `backend.createStack('FrogBotApp')` and Cognito logical ID overrides deliberately preserve the deployed CloudFormation identity. The destination nested stack name includes `FrogBotApp`; its **live** DynamoDB table, SNS topics, budget, schedule group, alarms, and log groups inherit that segment. Changing the stack name or logical IDs can replace resources. The destination Cognito pool's physical ID is opaque (`us-east-1_biJejrNQF`) and its display name is already HeyTim; do not replace it for a logical ID cleanup.
- **AgentCore:** `AgentCore-FrogBot-production` remains deployed with its old runtime, memory, gateway, evaluator, dataset, roles, and three `FrogBot*` identity-backed secrets. `AgentCore-HeyTim-production` already exists alongside it. Treat the old stack as a rollback dependency until direct traffic, memory, credentials, evaluation, and data-retention checks prove it is unused. Never change an AgentCore `name` merely for branding: that controls replacement.
- **S3:** The destination `frogbot-production-user-files-820323452649-us-east-1` bucket remains in the Amplify stack for rollback. A read-only listing found no current objects, object versions, or delete markers on this date. Its presence still affects a future stack change; confirm a fresh inventory and client references before removing it. The HeyTim bucket has current objects.

For any physical replacement, prepare a reviewed change set and dependency map first. Capture the current stack template, runtime/memory IDs, client outputs, backup/PITR state, queue and scheduler state, IAM grants, and retained secrets. Deploy parallel HeyTim resources; migrate and reconcile data and references; test authenticated API, bot replies, files, push, email, schedules, OAuth, and both Apple apps. Keep the prior infrastructure available through an observation window. If cutover fails, restore the recorded client/API/worker references and release configuration, reconcile writes made during the window, and only then consider cleanup. Do not delete old and new resources in the same first-cutover deployment.
